ABSTRACT
======================================================================

Secure Local Data Shredder is a local-first software prototype that
combines a Java command-line file-processing program with a Python
loopback HTTP bridge and a browser-based user interface. The Java
program contains file and folder workflows, dry-run previews, random-byte
overwriting using SecureRandom, metadata-marker handling for selected
text and image formats, backup and restore operations, and JSON-lines
audit logging. The Python bridge serves the frontend from the local
machine, stages files selected through the browser, and launches the Java
program. The frontend provides pass-count selection, Preview and Shred
modes, a confirmation gate, progress polling, a rough remaining-time
estimate, operation receipts, a session activity list, a theme preference,
and local validation-report controls.

The browser workflow deliberately operates on a copy written to the
project's uploads directory. The original selected in the browser stays
unchanged. In the command-line folder workflow, backups are created
before destructive processing, which can preserve recoverable copies.
These are material scope constraints, not incidental implementation
details. Overwriting a file does not ensure that storage-controller
remapping, snapshots, file-system journals, backups, or other copies have
been sanitized. The implementation is therefore appropriate for
education, demonstration, and controlled disposable-file testing, not
forensic or compliance certification.

The project was validated with a Java compilation check, Python syntax
analysis, editor diagnostics, and manual browser integration checks using
a disposable file. The checks exercised dry-run retention, staged-copy
overwrite/deletion, confirmation gating, live progress completion,
local-origin and staging-path guards, and responsive UI states. The
workspace does not contain a formal JUnit test suite. Results in this
report should be refreshed if the code changes after the recorded test
session.

Keywords: local-first processing, Java, Python, file handling, overwrite,
dry run, audit log, metadata, browser interface, staged file.

CHAPTER 1 - INTRODUCTION
======================================================================

1.1 Background

Users commonly delete files using an operating-system delete command.
That action generally removes a directory reference; the storage device
and file system determine when and whether the underlying blocks are
reused. A prototype shredder explores a different workflow: write data
across a file before asking the operating system to delete that file.
This can be educational, but the method's assurance depends on the file
system, storage medium, controller, and other retained copies.

1.2 Project overview

This project has two user paths. The Java CLI accepts local filesystem
paths and offers single-file/folder operations and supporting utilities.
The browser UI is served by a Python process on the loopback interface.
For browser-selected files, the bridge stores a local staging copy, then
invokes Java for preview or shredding. Browser selection is not a native
filesystem handle; accordingly, the browser workflow does not claim to
modify the original file.

1.3 Motivation

The project demonstrates how a destructive file operation can be made
more understandable through previews, explicit options, confirmation,
progress reporting, a visible completion receipt, and audit records. It
also demonstrates a hybrid architecture in which a small local HTTP
service connects a web UI to a Java process without sending file contents
to a remote service.

1.4 Project goals

- Provide a Java implementation for local file and folder operations.
- Demonstrate multi-pass random-byte overwrite followed by deletion.
- Provide a dry-run workflow and user confirmation for destructive CLI
  folder work and browser staged-copy shredding.
- Explore limited metadata-marker handling for selected formats.
- Record CLI operations in a local JSON-lines audit log.
- Provide backup and restore experiments for folder workflows.
- Provide a browser workflow with pass selection, progress, ETA, and
  operation result information.
- Explain honestly what this prototype can and cannot guarantee.

1.5 Organization of this report

Chapter 2 defines the problem, objectives, scope, and requirements.
Chapter 3 introduces relevant file-system and web concepts. Chapter 4
summarizes the iterative development and system requirements. Chapter 5
presents architecture and data flow. Chapter 6 describes implementation.

CHAPTER 3 - BACKGROUND AND RELATED CONCEPTS
======================================================================

3.1 File deletion and overwrite

A file API can replace the bytes visible through a file path and then
remove that path. This is not equivalent to issuing a device-level
sanitize command. File-system copy-on-write behavior, journaling,
snapshots, SSD wear levelling, remapped blocks, caches, and backups may
retain data. NIST media-sanitization guidance [1] distinguishes methods
and assurance levels according to media and risk. This project is not a
NIST-conformant implementation.

3.2 Random number generation

The Java implementation creates a SecureRandom instance and uses it to
fill an 8192-byte buffer for each write. SecureRandom is the Java API for
cryptographically strong random-number generation [2]. That choice does
not make the whole erasure process certified or guarantee that each
physical storage location is overwritten.

3.3 Local web bridge

The Python standard-library HTTP server binds to the IPv4 loopback
address and serves static assets and JSON endpoints. Loopback binding
means the service is intended for local access. It is not equivalent to
complete security: browser-origin checks, request validation, filesystem
containment, firewall conditions, and deployment practices also matter.
The server is a small prototype, not a hardened production web server.

3.4 Browser components

HTML structures the interface, CSS controls visual styling and responsive
layout, and JavaScript reads user input and calls the local service. The
browser File API supplies file bytes to the local upload request. Because
a web page normally does not receive arbitrary filesystem path access,
the Python bridge writes a local copy instead. The user sees and confirms
this scope before shredding.

3.5 Audit and backup concepts

The CLI appends timestamped JSON-line records with a path, pass count,
status, and message. This supports review but is not tamper-evident,
cryptographically signed, or privacy-minimized; paths can reveal local
user information. Folder processing makes a copy in a backup set before
shredding. That is useful for recovery during development, but it means
the file's content persists in the backup until the backup copy is
removed separately.

7. Connect the frontend to the bridge and show progress/result receipts.

5.4 Design decisions

- Staging copy: respects browser sandbox limits and makes destructive
  scope explicit, but does not erase the original.
- Separate preview and shred modes: reduces accidental operation risk.
- Pass-count selector: exposes the work factor to the user, while warning
  that extra passes do not guarantee SSD sanitization.
- Asynchronous job: lets the UI poll Java output rather than freezing for
  the duration of a shred run.
- Session activity and result receipt: improves user feedback; it is not
  proof of physical sanitization.
- Loopback service: supports local interaction without a cloud backend.

CHAPTER 6 - IMPLEMENTATION
======================================================================

6.1 Java CLI structure

Main.main creates a Scanner, repeatedly prints menu choices, obtains user
input, and routes to file, folder, dry-run, report, backup, restore, or
informational methods. The input model is line-oriented. The current
Java CLI and the browser bridge are separate entry points; the bridge
scripts menu choices into Java standard input.

6.2 Single-file overwrite logic

The main routine is Main.shredFile(Path filePath, int passes).

Figure 3. Single-file overwrite loop

Validate path exists and is a regular file
Read file size
Create SecureRandom and 8192-byte buffer
For each pass:
    Open target for overwrite (not append)
    While bytes remain:
        Fill buffer with random bytes
        Write the remaining chunk
        Emit progress checkpoint
    Flush and sync file descriptor
Delete file path

The implementation emits lines in the form:
SHRED_PROGRESS:<currentPass>:<totalPasses>:<bytesWritten>:<fileSize>

Python converts those values to job percentage. The progress calculation
is a UI estimate of bytes processed by the application, not a measure of
physical media sanitization.

6.3 Folder workflow

The CLI walks directories, gathers regular files, filters approved paths,
and can filter by risk category, extension, and filename substring. It
prints file/type/risk/size summaries. The destructive folder path calls
createBackupForFiles before shredding. This supports recovery but also
means that data remains in the created backup until that backup set is
explicitly deleted. Users must account for backup copies when evaluating
whether data has been removed.

6.4 Metadata handling

The Java code has preview and sanitizer routines for a narrow set of file
extensions. Text-like extensions include txt, log, md, csv, json, xml,
and html; the code removes lines matching a short list of metadata-like
labels. For PNG, selected textual and EXIF chunks are identified. The
JPEG-like path removes APP marker segments. The functions are not a
complete metadata implementation for all formats; notably, extension-
based checks and handcrafted binary parsing can miss cases or affect
valid files. Treat this as an experiment and do not promise universal
metadata removal.

In the browser path, the file operation is on the staged copy and invokes
the existing Java CLI flow. The operation receipt reports file identity,
size, passes, elapsed time, target state, and that the selected original
is unchanged; it does not show destroyed file content.

6.5 Backup and restore

The CLI writes timestamp-named folders beneath backup-restore, copies
selected input files, and creates a restore-manifest.txt mapping source
paths to backup copies. Restore previews valid manifest rows and asks
for confirmation when a Scanner is supplied. Backup health scores and
cleanup recommendations use local heuristics; they are not a backup
integrity certification. Backups contain potentially sensitive file
contents and must be handled as such.

6.6 Audit and generated reports

writeAuditEntry appends a JSON-shaped line to audit-log.json with a local
timestamp, target path, pass count, status, and message. Export methods
write text reports including audit-report.txt, final-shred-report.txt,
and backup-status-report.txt. Paths in audit records may be personally
identifying. The log is not signed or tamper-evident. The browser's Clear
history button clears only the visible current-session list, not the Java
audit log or exported reports.

6.7 UI implementation

The frontend is plain HTML, CSS, and JavaScript. The JavaScript:
- stages one selected browser file by POSTing FormData to /api/upload;
- toggles Preview and Shred modes;
- requires confirmation for shredding;
- polls /api/jobs/{id} every few hundred milliseconds;
- updates progress percentage and estimates remaining time from elapsed
  time and reported percentage;
- presents a result receipt and session events;
- changes light/dark theme and stores that preference in browser local
  storage when available.

The ETA is approximate and varies with file size, device performance,
file-system behavior, and application overhead. The theme preference is
not authentication and does not protect file operations.

6.8 Informational CLI options

Menu options 19-22 display text about zero-knowledge execution,
smart-contract destruction, AI metadata sanitization, and multi-cloud
architecture. These options are design/information screens, not working
blockchain, AI, cloud orchestration, or zero-knowledge implementations.

CHAPTER 8 - SECURITY, LIMITATIONS, AND RISK ASSESSMENT
======================================================================

8.1 Threat and trust model

The intended demonstration assumes one local user runs the bridge on the
same machine, chooses a disposable or understood file, and keeps the
bridge private to loopback. The system is not designed to defend against
an administrator, malware running as the same user, a compromised JDK or
Python runtime, all browser-to-localhost attack classes, or recovery of
remapped storage blocks.

8.2 Important limitations

1. Original versus staged copy. The browser uploads bytes to a new local
   staging file. Shred removes the staging file only; the source file
   remains. This is explicit in the interface.
2. Backups. CLI folder shredding creates backups before destructive
   processing. A backup may preserve the very data the user expects to
   remove. Delete the relevant backup copies separately when appropriate.
3. SSD and flash behavior. Wear levelling and remapping mean file-level
   overwrite cannot guarantee every physical block was overwritten.
4. File-system copies. Journals, snapshots, sync clients, caches, and
   backup systems may retain other copies.
5. Metadata scope. Handwritten format checks cover only selected markers
   and extensions, not every metadata element or file format.
6. Java path roots. getApprovedRoots includes user.home and user.dir plus
   a hard-coded project path. This is not a strong least-privilege policy
   and the hard-coded root harms portability.
7. Browser bridge. It binds to loopback and checks POST Origin and staging
   path. This is useful defense-in-depth, not a hardened security
   boundary; do not expose or port-forward the service.
8. Audit privacy. Audit records include full local paths and may expose
   usernames or directory names. The log is append-only by convention,
   not cryptographically protected.
9. Backup score. Health scoring is a simple heuristic and must not be
   marketed as a verified measure of data recoverability.
10. In-memory jobs. Job states are held in process memory; restarting the
    bridge loses active job state and job history.
11. Authentication. The app has no user login. A cosmetic browser login
    would not provide meaningful OS-level authorization.
12. Certification. The app has not been independently audited or
    certified against a sanitization standard.

8.3 Risk table

Table 6. Main risks and limitations

Risk                         Impact                         Mitigation / status
Wrong target file             Data loss                      Preview and explicit confirmation;
                                                             browser only targets staging copy
Backup survives shred         Data remains recoverable       Disclose and manage backups separately

                                                             sanitize procedures for high assurance

8.4 Ethical and safe use

Test on files created for this purpose. Do not run destructive operations
on someone else's files, systems, or backups without explicit
authorization. Do not describe an operation as complete if the app only
processed a staging copy. For regulated or high-assurance disposal,
follow current organizational policy, applicable NIST guidance, and the
storage-device manufacturer's sanitize capabilities.

CHAPTER 9 - CONCLUSION AND FUTURE WORK
======================================================================

9.1 Conclusion

The project demonstrates a local-first workflow connecting a Java
file-processing CLI to a Python loopback bridge and a browser UI. It
provides basic single-file and folder operations, preview workflows,
random-byte overwrite, selected metadata-marker logic, backups, reports,
audit logging, and visible browser progress for a staged copy. Usability
features such as mode selection, confirmation gating, activity history,
result receipt, and theme switching make the flow easier to demonstrate.

The central conclusion is deliberately limited: this prototype can
overwrite and delete a file path handled by the application, but it
cannot guarantee that all representations of the data are erased. The
browser feature is a staged-copy demonstration, and folder backups may
retain recoverable data. The design should not be represented as a
certified or production-grade secure erasure product.

9.2 Future work

- Replace the browser-upload workflow with a native desktop app and
  native file chooser, with carefully reviewed permissions and explicit
  target confirmation.
- Remove machine-specific paths and implement a testable, least-privilege
  target policy.
- Review the bridge against DNS rebinding, hostile origins, request-size
  abuse, race conditions, and local port collision.
- Add maximum upload size, cleanup policy for abandoned staging files,
  atomic operations, and robust cancellation/error recovery.
- Separate Java service methods from the interactive CLI so bridge calls
  do not need to script menu text.
- Add unit, integration, and UI regression tests and CI build checks.
- Use established metadata libraries and validate output files with
  format-specific parsers.
- Make backup retention and data persistence explicit before a shred run.
- Protect, minimize, rotate, or redact sensitive audit paths.
- Package with a signed Windows installer and bundled runtime where
  suitable, after security and portability review.
- For high-assurance media sanitization, integrate vendor/OS-supported
  device sanitization rather than relying only on file overwrite.

ANNEXURE B - DATA FLOW AND API SUMMARY
======================================================================

B.1 Browser selection
Browser File object -> multipart form request -> local Python process ->
UUID-prefixed file under src/uploads.

B.2 Preview
Browser sends staged path and pass count -> bridge validates path and
pass count -> Java CLI dry-run menu input -> textual preview result ->
bridge response -> browser result receipt. Preview does not overwrite or
delete the staged file.

B.3 Shred
Browser sends staged path, pass count, and confirm=true -> bridge checks
Origin and canonical staging path -> worker launches Java -> Java emits
progress lines -> bridge updates in-memory job -> browser polls job route
-> bridge reports complete only when Java reports success and staged path
is absent.

B.4 Local persistent files
- src/audit-log.json: Java CLI JSON-lines audit trail.
- src/audit-report.txt: human-readable audit export, if generated.
- backup-restore/: CLI backup sets and restore manifests, if generated.
- src/uploads/: browser staging copies; completed shred jobs remove their
  target staged copy, while abandoned copies can remain.
- validation-proof/: proof report location relative to Java process cwd.

Check the actual current working directory when locating generated files;
relative output paths depend on where the Java process is launched.
