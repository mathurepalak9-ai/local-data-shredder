VIVA AND PRESENTATION GUIDE

SECURE LOCAL DATA SHREDDER

Prepared from the current project implementation
Review date: 11 October 2026

Use this as a study aid, not as a script to claim features that are not
implemented. Personalize the presentation and verify the exact build
before demonstrating it.

======================================================================
1. PROJECT IN ONE MINUTE
======================================================================

Secure Local Data Shredder is a local-first prototype. Its core file
operations are implemented in Java. A Python bridge serves a browser UI
from the loopback address 127.0.0.1:8000 and invokes the Java program.
The browser lets a user select Preview or Shred, choose 1-7 overwrite
passes, confirm a destructive operation, view progress and an approximate
ETA, and inspect a result receipt. In this browser workflow, the app
copies the selected file to a local staging directory and operates only
on that staged copy. The original selected file remains unchanged. The
Java CLI also has folder, backup, restore, audit, and report utilities.
The project does not guarantee forensic erasure, especially on SSDs or
flash storage, and it is not a certified sanitization tool.

Opening
"My project is Secure Local Data Shredder. It demonstrates local file
handling, a Java overwrite routine, a Python loopback bridge, and a
browser interface. Its goal is to make a destructive workflow visible
and testable, while explaining its limits honestly."

Problem and objective
"Normal deletion does not necessarily overwrite data immediately. I
wanted to explore a local workflow with a preview, a deliberate
confirmation, progress feedback, audit records, and safer testing. This
is an educational prototype, not a forensic erasure guarantee."

Architecture
"There are three main runtime parts. Main.java implements the Java CLI
and file operations. local_bridge.py serves the HTML, CSS, and JavaScript
and starts Java as a subprocess. The browser communicates with the
bridge at 127.0.0.1:8000. The data path stays on this computer; there is
no cloud API in the application."

Demonstration
"I will choose a disposable file. The browser sends its contents to the
local bridge, which creates a staged copy in src/uploads. The original is
not changed. I can select Preview, which reports what the CLI would do
without overwriting or deleting the copy. Then I can switch to Shred,
select a pass count, check the confirmation, and run it. Java emits
progress checkpoints; Python exposes the job status; the browser polls
and displays progress, approximate remaining time, and a result receipt."

Safety note
"The displayed 100 percent means the application reports that its file
operation completed and the staged path is gone. It does not prove that

must be managed separately."

Close

interactive safety workflow. Future work would be a native desktop
file chooser, stronger target policy, automated tests, and device-aware
sanitization methods."

3. HOW THE APPLICATION WAS CREATED
======================================================================

Step 1: Define the local use case
The design starts with the requirement that the app process data on the
user's computer, not upload to a remote service. The current browser UI
uses a local bridge at 127.0.0.1 and stores staged content under the
project's src/uploads directory.

Step 2: Implement the Java command-line program
Main.java uses a menu loop to accept an operation and a path. It contains
single-file and folder workflows, dry-run modes, metadata helpers,
backup/restore utilities, reports, and audit entries. Java NIO types
such as Path and Files are used for file operations.

Step 3: Add the overwrite method
shredFile checks that the path exists and is a regular file. It reads the
file size, creates SecureRandom, and repeatedly writes an 8192-byte
buffer of random data for the configured number of passes. It flushes
and syncs each pass, emits progress lines, then calls deleteIfExists.
This is an overwrite-and-delete prototype, not a disk sanitization
command.

Step 4: Add CLI safety and supporting utilities
The CLI includes dry runs, path checks, folder scans and filters,
confirmation prompts, audit entries, and backup/restore utilities. The
folder shred path creates a backup before shredding. This is a recovery
feature, but backups preserve file contents and therefore have to be
considered separately in any data-removal decision.

Step 5: Create the local Python bridge
local_bridge.py uses Python's standard library HTTP server bound to
127.0.0.1:8000. It serves the frontend, accepts browser uploads, stages a
copy, validates that shred targets resolve inside src/uploads, and
starts Java using subprocess. It stores asynchronous job states in
memory so the UI can poll progress.

Step 6: Build the frontend
index.html describes the controls and status regions. styles.css defines
the layout, phone/desktop responsiveness, and light/dark themes. app.js
handles file selection, local requests, mode switching, confirmation,
progress polling, approximate ETA, activity entries, theme preference,
and the result receipt.

Step 7: Validate using disposable data
Compile Java, syntax-check Python, open the browser app, test a disposable
file with Preview, then shred only its staged copy. Check that the source
file remains. Check invalid origins and paths. Do not test destructive
operations against valuable files.

4. LANGUAGE AND TECHNOLOGY ANSWER
======================================================================

Question: How many languages did you use?

Defensible answer: "The project uses five implementation technologies:
Java for the core CLI and file operations, Python for the local HTTP
bridge and process orchestration, JavaScript for browser behavior, HTML
for page structure, and CSS for styling. Strictly speaking, Java,
Python, and JavaScript are programming languages; HTML is markup and CSS
is a style-sheet language."

Technology map:
- Java: src/Main.java; menu, local filesystem work, overwrite, metadata,
  backups, restore, logs, reports.
- Python: src/local_bridge.py; loopback HTTP service, static serving,
  staging, validation, subprocess, progress-job state.
- HTML: src/frontend/index.html; semantic controls and regions.
- CSS: src/frontend/styles.css; visual system, responsive design, theme.
- JavaScript: src/frontend/app.js; event handlers, fetch calls, polling,
  progress, receipt, activity, theme state.

======================================================================
5. FILE-BY-FILE EXPLANATION
======================================================================

src/Main.java
The main Java entry point. Main.main prints the CLI menu and routes
operations. shredFile performs the random overwrite/delete routine.
Other methods gather folders, filter files, inspect selected metadata,
create backups, restore copies, and write reports/audit rows.

src/local_bridge.py
The local-only web service. It serves frontend resources, handles the
browser upload, creates a UUID-prefixed staged file, validates staged
paths, runs Java, and stores/publishes job state. The server binds to the
IPv4 loopback interface on port 8000.

src/frontend/index.html
The HTML document. It provides the file picker, pass count, mode buttons,
confirmation checkbox, progress display, result receipt, session
activity, clear-history button, report actions, and theme toggle.

src/frontend/styles.css
Controls colors, layout, typography, button states, responsive behavior,
and light/dark presentation. It does not perform file operations.

src/frontend/app.js
Connects UI events to bridge endpoints. It stages browser files, sends
preview/shred requests, polls job IDs, updates progress, computes a
rough ETA, and renders outcomes. The browser-side Clear history action
only clears the visible activity list for the current page session.

README.md
Provides launch commands, runtime prerequisites, and safe manual testing
instructions.

run.ps1
Changes into src, compiles Main.java, and runs the Java CLI. It does not
start the browser app.

======================================================================
6. END-TO-END DATA FLOW
======================================================================

Browser file picker
  -> JavaScript reads File object
  -> multipart POST /api/upload to 127.0.0.1:8000
  -> Python writes a copy under src/uploads
  -> browser stores the returned staged path

Preview mode
  -> POST /api/dry-run {filePath, passes}
  -> Python confirms the path is inside staging
  -> Python feeds menu option 3 and inputs to Java
  -> Java reports a dry-run preview
  -> Browser retains the staged copy and shows a preview receipt

Shred mode
  -> User selects Shred staged copy and confirms
  -> POST /api/shred {filePath, passes, confirm:true}
  -> Python validates Origin, pass count, and canonical staging path
  -> Python starts a Java subprocess in a background thread
  -> Java emits SHRED_PROGRESS checkpoints
  -> Python calculates percentage and stores job state
  -> browser polls GET /api/jobs/{job_id}
  -> UI displays progress/ETA and terminal result
  -> successful job means staged path no longer exists

No step in the browser flow deletes the original browser-selected source.

7. LIKELY VIVA QUESTIONS AND ANSWERS
======================================================================

A. Project fundamentals

Q1. What is the project?
A. A local-first file-processing prototype combining a Java CLI, a
Python loopback bridge, and a browser frontend. It demonstrates preview,
random-byte overwrite, deletion of the targeted path, progress, logging,
and backup utilities.

Q2. What problem does it address?
A. It explores how a user can understand and control a local file removal
workflow better than with a bare delete command. It also demonstrates
integration between Java and a local browser UI.

Q3. What is the primary objective?
A. Provide an understandable local prototype with preview, explicit
configuration and confirmation, processing feedback, and an honest
account of data-erasure limits.

Q4. Is this production software?
A. No. It is a learning prototype. It lacks a formal automated test suite,
production packaging, independent security certification, and a
universal secure-erasure method.

Q5. Does the app upload content to the internet?
A. The intended runtime flow sends browser file bytes to the bridge bound
to 127.0.0.1 on the same computer. The project has no remote upload
service. A local-only design still needs careful security testing.

Q6. What is loopback?
A. 127.0.0.1 is the IPv4 loopback address; traffic is directed to a
service on the same machine rather than a remote host.

Q7. Which languages/technologies are used?
A. Java, Python, JavaScript, HTML, and CSS. Java/Python/JavaScript are
programming languages; HTML is markup and CSS is styling.

Q8. Why use both Java and Python?
A. Java contains the original CLI and file-processing logic. Python
provides a small local HTTP server and launches the Java process, which
lets the browser UI interact with that logic without rewriting it.

Q9. Is this a mobile/Android app?
A. No. The page is responsive and can fit phone-sized browser viewports,
but the project is not an Android APK or native app. The service and
JDK/Python prerequisites are desktop-oriented.

B. File and overwrite behavior

Q10. What does normal file deletion do?
A. It removes the file's directory entry; whether old bytes remain and
when they are reused depends on the OS, file system, and storage device.

Q11. How does shredFile work?
A. It validates the path, reads the file size, fills an 8192-byte buffer
with SecureRandom data, writes the file for each selected pass, syncs the
output, and calls Files.deleteIfExists.

Q12. Why use SecureRandom?
A. It is Java's API intended for cryptographically strong random-number
generation. That improves the byte source, but does not prove physical
media erasure.

Q13. Why multiple passes?
A. The UI exposes the count as a configurable demonstration of repeated
writes. More passes increase I/O and time, but should not be presented as
a guarantee, especially on SSD/flash media.

Q14. Does the browser shred the original file?
A. No. Browsers provide file contents through a sandboxed File object;
this implementation sends those bytes to local staging and shreds the
staged copy. The original source remains unchanged.

Q15. What does 100% progress prove?
A. It indicates the application reports the requested overwrite passes
completed and the staged path was deleted. It is not proof that every
physical block or other copy has been sanitized.

Q16. What happens if the file is empty?
A. The overwrite loop has no bytes to write, then it proceeds to delete
the file path. The progress logic needs special handling for zero size;
this case should be explicitly included in the maintained test suite.

Q17. Does overwriting work reliably on an SSD?
A. Not necessarily. Wear-levelling, remapped blocks, controller caches,
and file-system snapshots can keep prior data outside the file path.
Device-level sanitize or cryptographic erase methods may be needed for
higher assurance, depending on the device and policy.

Q18. Is metadata removal complete?
A. No. The CLI recognizes a limited set of text labels and selected PNG
or JPEG-like segments. It is a format-specific prototype and may miss
metadata. It is not a universal metadata sanitizer.

Q19. Why is the file size tracked?
A. It determines how many bytes to write and contributes to progress
calculation and the UI result summary.

Q20. What does flush/sync do?
A. It asks the stream/file descriptor to push buffered output toward the
underlying system before the pass closes. It does not bypass every
storage layer or prove physical sanitization.

C. UI, bridge, and security

Q21. Why use a Python bridge?
A. It serves static frontend files and provides local API routes. It can
launch Java as a subprocess and translate Java progress lines into
pollable job state.

Q22. How does progress reach the browser?
A. Java prints structured SHRED_PROGRESS lines. Python parses them,
updates a job dictionary under a lock, and returns it from
/api/jobs/{job_id}. JavaScript polls that endpoint and updates the
progress bar.

Q23. How is ETA calculated?
A. The frontend extrapolates from elapsed time and percent complete. It
is approximate and can be inaccurate when throughput changes.

Q24. What are the main endpoints?
A. GET /api/health, POST /api/upload, POST /api/dry-run, POST /api/shred,
GET /api/jobs/{id}, GET /api/proof, GET /api/proof-download, and
GET /api/backups.

Q25. How is a target restricted for browser shredding?
A. Python resolves the submitted path, checks that it is under the
resolved uploads directory, and requires it to be a regular file. The
bridge also checks the POST Origin against its local origins and requires
confirm=true for shred.

Q26. Is Origin checking enough for security?
A. No. It is one browser defense, not a complete security boundary. The
service needs a broader review for DNS rebinding, browser behaviors,
path races, request abuse, and local attackers. It should not be
forwarded or exposed externally.

Q27. Why does the Java CLI have a path policy?
A. To restrict where CLI paths may operate. The current policy includes
user.home, user.dir, and a hard-coded project directory; it is only a
prototype and is not a robust configurable allowlist.

Q28. Is there a login?
A. No. It is a single-user local prototype. A browser login alone would
not enforce OS permissions and could give misleading security assurance.

Q29. Does Clear history erase the audit log?
A. No. It empties only the visible session activity list in the current
page. The Java audit file and exported reports remain unchanged.

Q30. Where does theme preference live?
A. The JavaScript stores the light/dark preference in browser localStorage
when available. It stores a UI preference, not authentication data.

D. Backup, audit, tests, and operations

Q31. How do backups work?
A. Folder operations copy selected input files into a timestamped
backup-restore folder and write a restore manifest. The CLI has restore
and backup-management operations.

Q32. Is a file completely removed if there is a backup?
A. No. The backup contains another copy. A user must identify and manage
backup sets separately. That is a key limitation to mention in a demo.

Q33. What does the audit log record?
A. Local timestamp, target path, pass count, status, and message as
JSON-line records. It is not signed or tamper-evident and paths may
contain private information.

Q34. What tests are present?
A. The workspace has manual validation artifacts and development-session
checks, but no maintained JUnit test suite. For the demo, compile checks,
Python syntax checks, API guard checks, and disposable-file browser tests
were run.

Q35. How should this be tested safely?
A. Make a disposable file, choose Preview, verify it survives, then run a
confirmed shred and verify that only the staged copy is removed and the
source still exists.

Q36. What is the safe-path policy's main portability problem?
A. It includes the developer machine's absolute project path. It should
be removed in a production-quality update in favor of configured,
canonical, minimal allowed roots.

Q37. Are backup health scores authoritative?
A. No. They are code-defined heuristics based on characteristics such as
manifest presence, size, file count, and age. They do not verify file
content integrity or restore success.

Q38. What is the difference between a dry run and a real run?
A. A dry run previews actions and should not overwrite or delete the
staged target. A real run requires explicit confirmation and invokes the
overwrite/delete path.

Q39. What if the bridge restarts during a job?
A. Job state is in memory and is lost when the process exits. The actual
file may be partly overwritten or remain. Production work needs recovery,
interruption handling, and persistent job state.

Q40. What files should be protected before submission?
A. Audit logs, reports, staging files, backups, and sample documents may
contain local paths or sensitive content. Redact or exclude them when
appropriate and never include real confidential files.

E. Limitations and future improvements

Q41. What is the most important limitation?
A. The app cannot guarantee physical erasure across all storage types or
copies. Also, the browser operation shreds only a staged copy.

Q42. What would you improve first?
A. Make the UI a native desktop app with a native file chooser if the goal
is to operate on the original; remove the hard-coded path, add automated
tests, and document/confirm backup behavior. Then conduct a security
review before packaging.

Q43. Can this be distributed as an installer today?
A. It can be packaged technically, but it should not be marketed as
secure erasure software. Current users need Java and Python unless the
runtimes are bundled, and safety/portability work should precede a public
release.

Q44. Why is there no cloud feature?
A. The objective is local handling. Cloud deletion introduces remote
copies, credentials, APIs, and provider-specific retention behavior and
is outside this prototype's implementation.

Q45. Are blockchain, AI, zero-knowledge, or multi-cloud functions real?
A. No. Some CLI menu choices print design descriptions, but they do not
execute a smart contract, use an AI model, implement cryptographic
zero-knowledge proofs, or coordinate cloud providers.

Q46. What can the validation report prove?
A. It can summarize code/build or workflow checks recorded by the
application. A generated report is not an independent audit, forensic
analysis, or sanitization certificate.

Q47. What is the backup risk when shredding a folder?
A. The code creates backups before shredding. Those backup files remain
recoverable until deleted separately. This behavior must be disclosed
before the operation.

Q48. Can audit history be trusted as proof?
A. It is useful local bookkeeping, but it is not cryptographically
signed, tamper-evident, or independently verified. It should not be
presented as proof of physical erasure.

Q49. What is the difference between privacy and security here?
A. Keeping traffic local reduces remote exposure, but does not address
all local threats, file-system persistence, physical recovery, or
unauthorized use by a process already running as the same user.

Q50. What is the project conclusion?
A. It demonstrates a local multi-language file-processing workflow and
safety-oriented UI. Its value is educational; the implementation must
not overstate its erasure guarantee.

9. TECHNICAL TERMS TO REMEMBER
======================================================================

Loopback: network interface used by a machine to communicate with itself.

Staging copy: a separate local copy used as the browser workflow target.

Dry run: preview path that should not perform the destructive operation.

Pass: one full iteration of writing replacement bytes over file content.

SecureRandom: Java API for cryptographically strong random values.

Audit log: chronological application records; not inherently tamper-proof.

Backup manifest: mapping from original path to saved backup copy path.

Origin: browser security value describing the scheme, host, and port of a
web page; the bridge checks it for POST requests.

ETA: approximate remaining duration extrapolated from reported progress.

Sanitization: process for rendering access to target data infeasible under
a defined policy and threat model; this project does not certify that
level of assurance.

10. FINAL ANSWER STRATEGY IN A VIVA
======================================================================

When asked a difficult question:
1. State what the code actually does.
2. Distinguish an implemented feature from a design screen or future
   feature.
3. State what evidence supports the answer (method, endpoint, or test).
4. State the limitation without making an unsupported guarantee.
5. Suggest the next engineering step.

Example:
"The browser endpoint only accepts a canonical file path beneath the
staging folder. I tested a path outside that directory and it returned
HTTP 400. That is evidence for that check, not a full security audit. A
next step is automated path/race testing and a broader browser-to-local
threat review."
